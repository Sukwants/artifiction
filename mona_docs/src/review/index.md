# 代码审查

本说明供维护者和 AI 审查改动使用。审查对象由用户的请求和本次 diff 决定，不只包括游戏计算代码。

## 工作方式

用户仅要求审查时，读取和分析代码并输出发现，不自动修改实现、格式化文件或更新锁文件。用户同时要求修复时，按已授权范围完成修改并说明验证结果。

先确定比较基准、修改文件和工作区状态，再读取相关 diff 与调用关系。可以同时对照调用方、实现、持久化格式和文档；无需限制为每次只读一个文件，也不要为了一个局部问题遍历整个仓库。

优先检查能导致行为错误、数据丢失、兼容问题或明显性能退化的改动。风格偏好不应掩盖实际问题。结论应说明触发条件、影响、证据和可行修复方向。

## 按模块检查

| 改动 | 重点 |
| --- | --- |
| 角色、武器、圣遗物、Buff、目标函数 | 原始数值、触发条件、配置默认值、注册、属性来源和伤害类型 |
| 前端与响应式配置 | 输入到计算的转换、初始化顺序、联动、页面切换与异步状态 |
| 导入、Store 与存储 | 数据校验、覆盖/删除语义、账号隔离、已有数据兼容 |
| Worker、WASM 或扫描接入 | 消息协议、错误传播、取消、超时、结果归属和资源释放 |
| 构建、依赖与部署 | 命令、生成步骤、锁文件、平台差异、CI 实际覆盖范围 |
| 文档 | 路径与命令是否存在，用户可见功能是否已开放，源码与发布状态是否区分 |

游戏实现的详细检查项在 [checklist.md](checklist.md)，按涉及的模块逐项检查。需要理解公共计算接口时，从 [开发文档索引](../index.md)继续阅读；工程结构见 [architecture.md](../../../docs/architecture.md)。

原始资料通常在根目录 `prompt/`，目录被 Git 忽略。资料缺失时完成可确定部分，并标注无法验证的具体数据或条件；不要把推测写成已确认错误，也不要自动断言所有倍率正确。

## 输出与验证

发现应定位到具体文件和尽可能小的行范围，写明何种输入或操作导致什么结果。能够复现时描述必要步骤或给出最小样例。没有足够依据时标注不确定性。

验证与用户要求一致。文档和低影响改动通常检查相关文件即可；需要运行计算或浏览器场景时复用现有框架，避免接触用户的真实浏览器数据。明确列出已做的检查、未运行的检查和剩余限制。
